# SecureDrop Cloud 테스트 케이스 (B: 오탐·미탐·재검사 + 확장)

기대 결과는 `backend/detector.py`의 규칙(정규식 + RRN 체크섬 + 카드 Luhn, 카드는 14~19자리)을 기준으로 한다.
**배포 환경 재검증(2026-10-19): D-01~D-15, F-01~F-11, L-01~L-04 총 30건을 `/api/scan` 배포 주소로 실행했다. 27건은 현재 기대와 일치했고, 3건(D-06·F-03·F-05)은 13자리 숫자열이 카드로 중복·오탐되던 수정 전 규칙의 결과였다. 카드 최소 길이를 14자리로 올리는 수정(PR)으로 해결했으며 재배포 후 다시 확인한다(L-05는 정의상 미탐이라 생략).**

번호는 모두 테스트용 가짜 값이다.

실행 방법(서버 실행 후):

```powershell
Invoke-RestMethod http://localhost:8000/api/scan -Method Post `
  -Headers @{ Origin = 'http://localhost:5500' } `
  -ContentType 'application/json' -Body '{"text":"여기에 입력 값"}'
```

## 7. 실행 결과 요약

- 백엔드 자동 테스트: `cd backend && SCAN_FILE_MAX_MB=4 uv run pytest -q` → **69 passed**, `ruff check` 통과 (WSL, Python 3.12, 2026-10-20 기준 최신 `master` + 카드 길이 수정)
- 배포 환경 탐지 30건: 27건 기대 일치, 3건(D-06·F-03·F-05)은 수정 전 규칙의 결과라 아래 방침으로 수정
- 배포 환경 파일 검사 FI-01~07: 전부 기대 일치 (4MiB 통과, 4MiB+1 413, xlsx·pdf 415, 빈 파일 422, 응답에 원문 없음)
- **카드번호 방침(확정)**: 주민등록번호(13자리)가 우연히 Luhn을 통과해 CARD로 중복 집계되거나(F-05, D-06), 날짜가 틀린 13자리가 카드로 차단되는(F-03) 문제는 **카드 최소 길이를 13→14자리로 올려 해결**한다. 13자리 카드는 사실상 쓰이지 않으며 주요 카드는 15~16자리이다. 14자리 이상은 그대로 탐지한다(`test_thirteen_digit_numbers_are_not_cards`). 이 변경은 `detector.py` 한 곳이라 웹·확장·플러그인·정제에 똑같이 적용되며, 재배포해야 배포본에 반영된다.
- 한계(발표에 명시): 한글 숫자, 이름·주소, 체크섬이 틀린 임의 주민번호는 탐지하지 못한다(L-01~L-05).
