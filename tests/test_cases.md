# SecureDrop Cloud 테스트 케이스 (B: 오탐·미탐·재검사 + 확장)

기대 결과는 `backend/detector.py`의 규칙(정규식 + RRN 체크섬 + 카드 Luhn)을 읽고 계산한 값이다.
**배포 환경 재검증(2026-10-19): D-01~D-15, F-01~F-11, L-01~L-04 총 30건을 `/api/scan` 배포 주소로 실행해 모두 기대 결과와 일치했다(L-05는 정의상 미탐이라 생략).**

**실제 서버에서 한 번 실행해 "실제 결과" 열을 채운 뒤 발표 자료에 쓴다.** 번호는 모두 테스트용 가짜 값이다.

실행 방법(서버 실행 후):

```powershell
Invoke-RestMethod http://localhost:8000/api/scan -Method Post `
  -Headers @{ Origin = 'http://localhost:5500' } `
  -ContentType 'application/json' -Body '{"text":"여기에 입력 값"}'
```

## 2. 오탐 방지: 통과해야 하는 정상 입력

| ID | 입력 | 기대 결과 | 이유 | 실제 결과 |
|---|---|---|---|---|
| F-01 | `02-123-4567` (유선 번호) | 통과 | 휴대폰 접두(010 등) 아님 | 통과 ✅ |
| F-02 | `010-12-3456` | 통과 | 자릿수 부족 | 통과 ✅ |
| F-03 | `901301-1234568` (13월) | CARD 1 (13자리 숫자열이 우연히 Luhn 통과) | RRN 날짜 검증 실패 | **CARD 1로 차단됨 (예상과 다름 ⚠)** |
| F-04 | `900101-1234567` (체크섬 틀림) | 통과 | RRN 체크섬 실패 | 통과 ✅ |
| F-05 | `850315-2201237` (유효 RRN) | **RRN 1과 CARD 1이 함께 나올 수 있음** | 13자리 숫자열이 Luhn도 우연히 통과 → 한 값이 두 유형으로 집계되는 오탐. 차단 여부는 맞지만 유형이 부정확함 | RRN 1, CARD 1 (예상대로 중복 집계) |
| F-06 | `1234 5678 1234 5678` | 통과 | Luhn 실패 | 통과 ✅ |
| F-07 | `1111111111111111` | 통과 | 같은 숫자 반복 제외 규칙 | 통과 ✅ |
| F-08 | `sk-test` | 통과 | 키 길이(20자) 미달 | 통과 ✅ |
| F-09 | `주문번호 20261019123456` | 통과 | 날짜·체크섬·Luhn 모두 실패하는지 확인 | 통과 ✅ |

## 7. 실행 결과 요약 (WSL, Python 3.12, `detector.scan` 직접 호출)

- 백엔드 자동 테스트: `uv run pytest -q` → **69 passed**
- 탐지 15건(D-01~15) 모두 기대대로 차단. L-01~05는 기대대로 미탐(한계).
- 오탐 11건 중 10건은 기대대로 통과. 예외 1건:
  - **F-03** `901301-1234568`(13월이라 RRN은 아님)이 **CARD로 차단**됨. 13자리 숫자열이 우연히 Luhn 검사를 통과한다. 13~19자리 숫자열은 날짜·체크섬이 틀려도 약 10% 확률로 CARD로 잡히는 구조다.
  - **F-05**: 유효 RRN이 RRN과 CARD로 중복 집계됨.
- 개선 제안(A에게 전달): 카드번호 길이를 13자리 제외(주요 카드는 15~16자리), 또는 RRN 형식(`\d{6}-?[1-4]\d{6}`)과 겹치는 13자리는 CARD에서 제외.
